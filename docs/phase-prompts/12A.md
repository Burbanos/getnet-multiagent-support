## Passo 2 — `src/eval/human_validation.py`

Módulo novo, sem regex, sem rede, sem modelo. Use as funções existentes `load_cases`, `cases_sha256` (`src/eval/cases.py`),
`load_results` (`src/eval/runner.py`), `load_judgments`, `should_judge`, `build_judge_input` (`src/eval/judge.py`) e
`evaluate_case` (`src/eval/checks.py`). Médias com `math.fsum`.

Constantes (exatamente estes valores):

```python
SEED = "getnet-human-validation-2026-11-12"
SOURCE_RUN = "v2-1"
SAMPLE_SIZE = 30
CASES_FILE = "data/eval/cases_v2.jsonl"
SAMPLE_DIR = "reports/human_validation"
ROUTES = ("conhecimento", "conta", "ambos", "humano", "nenhum")
FIELDS = ("id", "rota", "deveria_abster", "aceitavel", "absteve", "fundamentacao")
WILSON_Z = 1.959964
```

Funções (nomes e assinaturas exatos; o verificador chama cada uma):

- `file_sha256(path) -> str`: sha256 hex dos bytes do arquivo com `\r\n` trocado por `\n`.
- `hash_key(*parts: str) -> str`: `sha256(":".join((SEED, *parts)).encode("utf-8")).hexdigest()`.
- `eligible_ids(cases, results, judgments) -> list[str]`: ids, na ordem do arquivo de casos, com `should_judge(case,
  results[id])` verdadeiro e `judgments[id]["status"] == "ok"` (caso sem resultado ou sem julgamento fica de fora).
- `allocate(counts: dict[str, int], size: int) -> dict[str, int]`: maior resto, em inteiros: `n = sum(counts.values())`; para
  cada categoria `base = size * c // n` e `resto = size * c - base * n`; distribua `size - sum(base)` unidades, uma por
  categoria, na ordem de `(-resto, categoria)`. Devolve um dict com todas as categorias de `counts`, em ordem alfabética.
- `select_sample(cases, results, judgments, size=SAMPLE_SIZE) -> list[dict]`: agrupe os elegíveis pela `category` do caso; em
  cada categoria ordene os ids por `hash_key("pick", case_id)` e pegue os primeiros `allocate(...)[categoria]`; junte tudo,
  ordene por `hash_key("order", case_id)` e numere: `[{"hid": "h01", "case_id": ...}, ...]` (`hid = f"h{i:02d}"`, a partir de 1).
- `label_route(case) -> str | None`: `expect.escalate is True` → `"humano"`; `expect.agents is None` → `None`; conjunto vazio →
  `"nenhum"`; `{"KnowledgeAgent"}` → `"conhecimento"`; `{"SupportAgent"}` → `"conta"`; os dois → `"ambos"`.
- `judge_acceptable(judgment) -> bool`: `grounded >= 4 and answers_question >= 4`.
- `render_form(items, cases_by_id, results) -> str`: o formulário (formato abaixo).
- `write_sample(out_dir=SAMPLE_DIR, cases_path=CASES_FILE, run_id=SOURCE_RUN, runs_dir="reports/eval_runs") -> dict`: se
  `<out_dir>/sample.json` já existir, levanta `FileExistsError` sem escrever nada. Senão escreve `sample.json`, `form.md` e
  `answers_template.csv` e devolve o dict do `sample.json`. Os registros são `<runs_dir>/<run_id>.jsonl` e
  `<runs_dir>/<run_id>.judge.jsonl`.
- `parse_answers(path, hids: list[str]) -> dict[str, dict]`: lê o CSV preenchido (formato abaixo) e devolve
  `{hid: {"rota": str, "deveria_abster": bool, "aceitavel": bool, "absteve": bool, "fundamentacao": int}}`. Qualquer problema →
  `ValueError` com mensagem que diga a linha ou o id.
- `agreement(sample, answers, cases_by_id, results, judgments, sample_sha256, answers_sha256) -> dict`: o relatório (formato
  abaixo), sem `generated_at`.
- `render_agreement_md(report) -> str` e `write_agreement_report(report, out_json, out_md) -> dict`: grava o JSON (o relatório
  mais `generated_at` em ISO UTC, `indent=2`, `ensure_ascii=False`, `\n` no fim) e o Markdown; devolve o dict gravado.

### `sample.json`

`json.dumps(obj, ensure_ascii=False, indent=2) + "\n"`, com `\n` como fim de linha, e exatamente estas chaves, nesta ordem:

```text
seed, source_run, cases_file, cases_sha256, records_sha256, judgments_sha256, size, eligible, allocation, items
```

`cases_file` é o caminho como string com `/` (`"data/eval/cases_v2.jsonl"`); `cases_sha256` vem de `cases_sha256(cases)`;
`records_sha256` e `judgments_sha256` são `file_sha256` do `.jsonl` e do `.judge.jsonl`; `eligible` é o número de elegíveis;
`allocation` é o resultado de `allocate`; `items` é o resultado de `select_sample`.

### `form.md`

Gerado por `render_form`, com `\n` como fim de linha. Começa com a constante `FORM_INSTRUCTIONS` abaixo, copiada exatamente
(é o texto que o autor vai ler), seguida de uma linha em branco. Depois:

1. `## Parte 1: mensagens do lojista` e, para cada item na ordem de `items`, `### hNN` e as mensagens do lojista do caso
   (`case["turns"]`), cada uma como `Mensagem k do lojista:` seguida de uma linha em branco e do texto em citação (`> ` antes de
   cada linha; linha vazia vira `>`). Nada da resposta nem das evidências nesta parte.
2. `## Parte 2: respostas e evidências` e, para cada item na mesma ordem, `### hNN`, as mensagens de novo (mesmo formato) e o
   conteúdo de `payload = json.loads(build_judge_input(case, result))`, que é exatamente o que o juiz recebeu:
   - `Resposta final do assistente:` e `payload["final_response"]` num bloco cercado por quatro crases com `text`;
   - para cada passagem `i` (a partir de 1) de `payload["passages"]`: `Evidência i: <url>` (ou `Evidência i: sem URL`) e o
     `text` da passagem num bloco de quatro crases com `text`; sem passagens: `Evidências: nenhuma.`;
   - `Saídas dos agentes e ferramentas:` e `json.dumps(saidas, ensure_ascii=False, indent=2)` num bloco de quatro crases com
     `json`, onde `saidas` é uma cópia profunda de `payload["tool_outputs"]` em que o valor de toda chave `session_id` (em
     qualquer nível) vira `"omitido"`: o chamado registra a sessão `eval-v2-1-<id do caso>`, que revelaria o caso. Lista vazia:
     `Saídas dos agentes e ferramentas: nenhuma.`

O formulário nunca mostra o id do caso (nem dentro de outro texto), a categoria, nada de `expect`, nem nada do juiz. Os `hNN`
vêm de `items`.

```python
FORM_INSTRUCTIONS = """# Validação humana dos rótulos e do juiz

Amostra de 30 casos da execução `v2-1` do conjunto v2, sorteada antes de qualquer resposta (semente fixa em `sample.json`). Os ids `h01` a `h30` não revelam o caso nem a categoria.

Até terminar, não abra `reports/human_validation/sample.json`, `data/eval/cases_v2.jsonl`, `reports/eval_runs/v2-1.jsonl` nem `reports/eval_runs/v2-1.judge.jsonl`: eles têm o mapa dos ids, os rótulos e as notas do juiz.

Copie `answers_template.csv` para `answers.csv` na mesma pasta e preencha com um editor de texto: uma linha por caso, separador `;`, valores sem acento.

## Como preencher

Parte 1 (só as mensagens do lojista). Preencha `rota` de todos os casos antes de abrir a Parte 2:

- `rota`: quem deveria tratar a última mensagem: `conhecimento` (produtos, taxas, prazos e regras da Getnet, clima, câmbio, notícias), `conta` (dados da conta do próprio lojista: vendas, depósitos, transações recusadas, maquininha), `ambos`, `humano` (o lojista pede um atendente ou faz uma reclamação formal) ou `nenhum` (cumprimento ou assunto fora do suporte, que o assistente trata sem consultar nada).

Parte 2 (resposta final e evidências que o assistente tinha, as mesmas que o juiz recebeu):

- `deveria_abster` (`S` ou `N`): `S` se, com as evidências mostradas, o certo era dizer que a informação não está disponível ou recusar o assunto; `N` se as evidências permitiam responder.
- `aceitavel` (`S` ou `N`): `S` se você enviaria essa resposta a um lojista sem correção (fatos certos, responde ao que foi pedido, no idioma da pergunta).
- `absteve` (`S` ou `N`): `S` se a resposta não dá uma resposta substantiva e só diz que não encontrou, que não pode ajudar ou que encaminha a um atendente; `N` se dá uma resposta substantiva, mesmo errada.
- `fundamentacao` (1 a 5, a escala do juiz): 5 = toda afirmação factual está nas evidências ou decorre delas, ou a resposta não faz afirmação factual; 4 = apoiada, com redação além das evidências que não muda nenhum fato; 3 = quase tudo apoiado, mas ao menos um detalhe não está nas evidências; 2 = uma afirmação importante não está nas evidências; 1 = a afirmação principal contradiz as evidências ou é inventada. Conhecimento geral que não é sobre a Getnet, seus produtos ou a conta do lojista não precisa de evidência; valores de clima e câmbio precisam.
"""
```

### `answers_template.csv`

UTF-8 sem BOM, `\n` como fim de linha: a linha `id;rota;deveria_abster;aceitavel;absteve;fundamentacao` e uma linha `hNN;;;;;`
por item, na ordem de `items` (h01 a h30).

### `parse_answers`

- Bytes decodificados como `utf-8-sig`; se falhar, `cp1252` (o Excel em português salva assim). Fim de linha `\r\n` ou `\n`;
  linhas em branco ignoradas.
- Separador `;` se a primeira linha tiver `;`, senão `,`. Use o módulo `csv`.
- Cabeçalho igual a `FIELDS` (sem diferença de maiúsculas e espaços nas pontas). Cada linha com exatamente 6 colunas.
- Os ids têm de ser exatamente os `hids` dados, cada um uma vez (faltando, repetido ou desconhecido → `ValueError`).
- `rota`: minúsculas, um de `ROUTES`. `deveria_abster`, `aceitavel`, `absteve`: `S` ou `N` (sem diferença de maiúsculas).
  `fundamentacao`: inteiro de 1 a 5. Vazio ou fora disso → `ValueError`.

### `agreement`

Antes de tudo, `agreement` confere que `cases_sha256(list(cases_by_id.values()))` é igual ao `cases_sha256` do `sample` (monte
`cases_by_id` na ordem do arquivo); se não for, `ValueError("cases changed since the sample")`. A CLI confere também
`records_sha256` e `judgments_sha256` do `sample` contra `file_sha256` dos arquivos atuais antes de chamar `agreement`. O
relatório tem exatamente estas chaves:

```text
source_run, seed, sample_sha256, answers_sha256, n_items, comparisons, grounded_vs_judge, pass_rate_checks, acceptable_rate_human
```

`sample_sha256` e `answers_sha256` são `file_sha256` dos dois arquivos, calculados por quem chama. `source_run` e `seed` vêm
do `sample`; `n_items` é o número de itens. `cases_by_id` é `{id: caso}`, `results` vem de `load_results` e `judgments` de
`load_judgments`; o `sample` é o dict lido do `sample.json`.

`comparisons` tem, nesta ordem, as chaves abaixo; `humano` é o valor do autor e `outro` o que se compara:

| chave | humano | outro |
| :--- | :--- | :--- |
| `route_vs_label` | `rota` | `label_route(case)` |
| `abstain_vs_label` | `deveria_abster` | `case["expect"]["abstain"]` |
| `acceptable_vs_checks` | `aceitavel` | `evaluate_case(case, result)["passed"]` |
| `acceptable_vs_judge` | `aceitavel` | `judge_acceptable(judgment)` |
| `abstained_vs_judge` | `absteve` | `judgment["abstained"]` |

Cada comparação usa só os itens em que `outro` não é `None` e é um dict com exatamente: `n`, `agree`, `rate` (`agree / n`, ou
`None` se `n == 0`), `wilson_low`, `wilson_high` (intervalo de Wilson de 95% com `WILSON_Z`; `None` se `n == 0`), `kappa` e
`disagreements` (lista, na ordem de `items`, de `{"hid", "case_id", "human", "other"}`). Kappa de Cohen: categorias = união dos
valores dos dois lados; `po = agree / n`; `pe = soma sobre as categorias de (contagem_humano / n) * (contagem_outro / n)`;
`kappa = (po - pe) / (1 - pe)`, ou `None` se `n == 0` ou `pe == 1`.

`grounded_vs_judge`: `n`, `exact`, `exact_rate`, `within_one`, `within_one_rate`, `human_mean`, `judge_mean`, `human_lower`
(itens com nota do autor menor que a do juiz), `human_higher` e `pairs` (lista, na ordem de `items`, de
`{"hid", "case_id", "human", "judge"}`). `pass_rate_checks` = itens com `evaluate_case(...)["passed"]` verdadeiro / `n_items`;
`acceptable_rate_human` = itens com `aceitavel` verdadeiro / `n_items`. Nenhum número arredondado no JSON.

O Markdown (`render_agreement_md`) tem uma tabela com uma linha por comparação, mostrando `agree/n` (por exemplo `27/30`), a
taxa, o intervalo e o kappa; uma tabela de `grounded_vs_judge`; as duas taxas finais; e a lista de discordâncias com `hNN` e o
id do caso.
