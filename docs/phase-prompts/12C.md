## Passo 2 — `src/core/notifier.py` (webhook, sem texto da conversa)

```python
@dataclass(frozen=True)
class NotificationResult:
    status: str             # "sent" | "failed" | "disabled"
    error_type: str | None  # "http_<código>" ou o nome da classe da exceção; None quando sent ou disabled
    http_status: int | None

def build_payload(ticket: dict) -> dict: ...
class OperatorNotifier:
    def __init__(self, url: str | None = None, timeout_s: float | None = None, client: httpx.Client | None = None): ...
    def notify(self, ticket: dict) -> NotificationResult: ...   # nunca levanta exceção
def get_notifier() -> OperatorNotifier: ...                     # singleton com as configurações
def reset_notifier() -> None: ...
```

- `build_payload`: com `url = settings.PUBLIC_BASE_URL.rstrip("/") + "/tickets/" + ticket_id`, devolve exatamente
  `{"text": f"Novo chamado {ticket_id} (prioridade {priority}) aguardando o atendimento humano: {url}", "ticket_id",
  "priority", "created_at", "url"}`. Nada do motivo, da transcrição nem do `user_id`. O campo `text` faz o mesmo JSON servir para
  webhooks de entrada do Slack, Google Chat e Teams.
- `notify`: `url` vazio → `disabled`, sem requisição. Senão `POST` JSON com o `client` injetado (ou um `httpx.Client` com o
  timeout), `timeout=OPERATOR_WEBHOOK_TIMEOUT_S`: 2xx → `sent`; outro código → `failed`, `http_<código>`; qualquer exceção →
  `failed` com o nome da classe. Em todos os casos, `metrics.inc_notification(status)` e um log `operator notification` com
  `status` em `extra` (sem URL nem conteúdo).
- `src/core/metrics.py`: `inc_notification(status)` (`sent`, `failed`, `disabled`; outro valor vira `unknown`), zerado em
  `reset()`, e no `render()` o contador `getnet_operator_notifications_total{status="..."}` com `# HELP` e `# TYPE` sempre
  presentes.

## Passo 3 — Chamados e a ferramenta de escalonamento

- `src/core/tickets_db.py`: colunas `notified_at TEXT` e `notification_status TEXT` no `CREATE TABLE` e na migração de tabelas
  antigas (como as outras colunas). Novo método `record_notification(ticket_id, status) -> bool`: grava o status e
  `notified_at` (ISO UTC só quando `status == "sent"`, senão `NULL`); `False` se o chamado não existe.
- `src/tools/agent_tools.py`, `escalate_to_human`: depois que `create_ticket` deu certo, chame `get_notifier().notify(ticket)` e
  `repo.record_notification(ticket_id, result.status)` dentro de um `try` próprio (`except Exception` com log sem texto). Uma
  falha da notificação nunca desfaz nem esconde o chamado, e a saída JSON da ferramenta continua exatamente a de hoje.

## Passo 4 — Retomada do turno quando o operador responde (`src/core/state.py`, `src/core/graph.py`)

- `SupervisorState` ganha `operator_event: dict[str, Any] | None`. `run_sync` passa `"operator_event": None` no estado de
  entrada de todo turno do lojista.
- Constante `OPERATOR_MESSAGE_PREFIX` em `graph.py`, exatamente:

```python
OPERATOR_MESSAGE_PREFIX = (
    "[Resposta do atendente humano ao chamado {ticket_id}. Esta mensagem é do atendente, não do lojista. / "
    "Reply from the human support agent for request {ticket_id}; this message is from the agent, not from the merchant.]\n\n"
)
```

- Grafo: a entrada deixa de ser `START → guardrail` e passa a ser uma aresta condicional de `START`: com `operator_event` →
  novo nó `operator_resume`; senão → `guardrail` (o resto do grafo não muda). `operator_resume → supervisor`. O nó
  `operator_resume` devolve `pending_ticket_id: None`, `operator_event: None` e `handoff: {"ticket_id": ..., "status":
  "operator_reply"}`. Turnos do operador não passam pelo guardrail nem pelo classificador (o operador é autenticado e confiável).
- `handoff_gate`: novo caso, antes de "fechado sem resposta": chamado com `operator_reply` **e** `delivered_at` já preenchido →
  `pending_ticket_id: None`, `handoff: {"ticket_id", "status": "resumed"}` e segue para o classificador/supervisor (a resposta
  já foi entregue pela retomada; a conversa não pode ficar presa em "pendente").
- `OrchestrationGraph.resume_after_operator(ticket_id) -> dict`, nesta ordem:
  1. Chamado inexistente, sem `operator_reply` ou sem `session_id` → `{"status": "skipped", "reason": "no_reply"}`; já com
     `delivered_at` → `skipped`, `already_delivered`.
  2. Thread `f"{user_id}:{session_id}"` do chamado: se o `pending_ticket_id` do estado não for esse chamado → `skipped`,
     `not_pending`, sem marcar entrega.
  3. `repo.mark_delivered(ticket_id)`; `False` → `skipped`, `already_delivered`.
  4. Resposta mascarada com `sanitize_pii` (nada cru entra no checkpoint). Invoca o grafo nessa thread com o mesmo estado de
     entrada por turno de `run_sync` (listas vazias, `ticket`/`handoff` `None`, contadores por turno zerados, `trace_id` novo),
     `operator_event: {"ticket_id": ticket_id}` e `messages: [HumanMessage(content=OPERATOR_MESSAGE_PREFIX.format(...) +
     resposta mascarada, id=<uuid>, additional_kwargs={"origin": "operator"})]`, dentro de `bind(...)` como `run_sync`.
     Sucesso → `{"status": "resumed", "final_response": ...}`.
  5. Qualquer exceção → `_close_dangling_tool_calls(config, <classe>)` e `update_state(config, {"messages":
     [AIMessage(HANDOFF_REPLY_PREFIX.format(ticket_id=...) + resposta mascarada)], "pending_ticket_id": None,
     "operator_event": None, "final_response": <o mesmo texto>, "handoff": {"ticket_id", "status": "delivered"}},
     as_node="abstention_check")` → `{"status": "delivered_verbatim", "error_type": <classe>}` (a entrega literal de hoje, só que
     imediata). Se até isso falhar → `{"status": "failed", "error_type": ...}`. Nunca levanta exceção.
  6. Um log `operator resume` com `status` em `extra`, sem texto.
- `OrchestrationGraph.session_messages(user_id, session_id, limit=50) -> list[dict]`: as mensagens da thread
  `f"{user_id}:{session_id}"` que o lojista vê, na ordem: `HumanMessage` sem `origin == "operator"` → `{"id", "role":
  "customer", "content"}`; `AIMessage` sem `tool_calls` e com texto → `{"id", "role": "assistant", "content"}`. Mensagens de
  ferramenta e do operador ficam de fora. As últimas `limit`. Thread inexistente → `[]`.

## Passo 5 — Corte do histórico

`OrchestrationGraph._trim_history(config)`, chamado depois de cada `graph.invoke` bem-sucedido em `run_sync` e em
`resume_after_operator`: com `MAX_HISTORY_MESSAGES = n > 0` e mais de `n` mensagens na thread, procure o primeiro índice
`i >= len(mensagens) - n` cuja mensagem é `HumanMessage`; se existir e for maior que 0, remova as mensagens `[0, i)` com
`RemoveMessage(id=...)` via `update_state(config, {"messages": [...]}, as_node="abstention_check")`. Sem `HumanMessage` nessa
janela (um único turno maior que o limite), não corta. Nunca levanta exceção (log sem texto). Os checkpoints antigos continuam
no SQLite: isso fica como limitação no README da 12E.

## Passo 6 — API e `/demo` (`src/main.py`, `src/static/demo.html`)

- `PATCH /tickets/{ticket_id}` vira função síncrona (`def`, para o FastAPI rodá-la no pool de threads). Validação e erros como
  hoje. Quando o corpo traz `reply` e a atualização deu certo, chame `get_orchestrator().resume_after_operator(ticket_id)` (uma
  exceção inesperada vira `{"status": "failed", "error_type": ...}`, com log sem texto) e responda o chamado relido do banco
  mais a chave `"resume"`. Sem `reply`, `"resume": None`.
- `GET /sessions/{session_id}/messages`: só papel `customer` (operador → 403; sem chave → 401); `session_id` de 1 a 64
  caracteres (senão 422); lê a thread do próprio lojista (`principal.user_id`) e responde
  `{"session_id": ..., "messages": get_orchestrator().session_messages(principal.user_id, session_id)}`.
- `/demo`: depois de uma resposta do `/chat` com `metadata.ticket` ou `metadata.handoff.status == "pending"`, comece a consultar
  `/sessions/{session_id}/messages` com o mesmo `X-API-Key` a cada 5 s (`setInterval`). A primeira leitura marca as mensagens
  já vistas; mensagens novas com `role == "assistant"` são mostradas no chat e a consulta para (`clearInterval`). Pare também
  depois de 10 minutos. Nada mais muda na página.
